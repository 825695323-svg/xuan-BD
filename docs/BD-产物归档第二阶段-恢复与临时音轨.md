# BD 产物归档第二阶段：明确恢复与视频临时音轨

## 本轮修改

1. 新增 `artifact.restore`（已归档产物按需恢复工具）。只接受源任务 `sourceTaskId`（原任务编号）以及已发布的 `fileRefId`（原文件引用）；核对 `artifact_archive_receipts`（既有产物归档账本）的 `confirmed`（元数据已确认）状态、原账号绑定、原文件版本和 SHA-256（原内容摘要）。远端首先按路径/大小/`fs_id`（对象编号）查询，明确下载后核对实际字节 SHA-256；成功后以新 `fileRefId` 发布，不覆盖或修改原文件引用。
2. 改进 `artifact.archive`（跨格式归档工具）的再次核对：曾经持久登记的归档，即使原本地文件已经缺失，也可依据冻结记录只读查询原网盘路径、大小和对象编号。首次上传仍必须从本地已登记文件读取和核对完整字节。重新核对不会生成第二次上传。
3. 修改 `platform/capabilities/transcription/video.ts`（公开视频链接转写）：当平台没有原生字幕而临时下载音轨时，该音轨只在 `DirectWorkspace`（受控暂存工作区）存在，转写完成后不再发布 `video-source-*`（长期原音频副本）。任务回执保留视频 URL、音轨摘要、原始字节长度和 `localRetained:false`（本地音轨未保留）。如平台有原生字幕，仍按原规则保存字幕源引用。Whisper 已经生成的 `transcript.txt`（转写文本）直接用于最后发布，避免在临时目录复制第二份同一正文。
4. 保留本地音频/视频文件处理接口的原始 `fileRefId`（本地材料引用），不因视频 URL 的临时音轨处理而擅自改变用户上传媒体的保管语义。

## 安全与兼容边界

- `artifact.archive`（归档）成功只证实网盘文件名、大小和编号一致；完整字节一致性只在用户明确调用 `artifact.restore`（按需恢复）后核验。
- `artifact.restore`（恢复）成功后产生新的、单独登记的本地文件引用；旧文件引用不会偷偷改指新文件，旧的 R1（正式结构化交接）或检索任务仍然使用原引用。
- 不自动删除任何历史原件、采集产物、材料数据库 BLOB（原字节对象）、WFD（正式金融数据仓库）快照和索引。
- 不添加 Harness 主动推送、后台自动归档或自动恢复；只有已授权的 BD AGENTS（BD 会话代理）任务明确调用工具。
- 单文件仍受 `CLOUD_MAX_BYTES`（256 MiB 网盘归档字节预算）限制；超过上限时保留原件并明确报告，不拆包绕过预算。
- 视频 URL 的无字幕音轨只作临时内容；旧的 `source.fileRefId`（原文件编号）在这种情况下改为 `source.kind='remote-audio-temporary'`（临时远端音轨来源记录），包含摘要与来源 URL，而不是伪造本地持久文件引用。

## 验收与未完成项

- GitHub Actions（自动构建/测试）运行 TypeScript（类型检查）、前端构建和百度网盘相关隔离测试；真实网盘账号与真实视频平台未在自动测试中授权执行。
- **仍未实现自动回收已归档文件**：现有 `FileReferenceService`（本地文件引用服务）的消费者通过本地路径读文件，当前按需恢复创建的是新引用，不可因此删除旧文件。
- 接口源/网页来源正式入库后怎样自动挑选最小证据清单、如何迁移下游引用和五步加工的持久中间对象回收，均属于后续工作，不能算本轮完成。
