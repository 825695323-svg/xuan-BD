## 二、已确认的接线问题

### A01｜高：七个新产物动作没有进入会话模型允许表

证据：`modules/agent/model-tools.ts` 的 `MODEL_ACTIONS`（模型允许调用动作集合），以及 `apps/server/services.ts` 的新动作装配；实际 `runtime-wiring-probes.json`。

以下动作在真实宿主的技能注册表里存在，但全部不在模型允许表中：

`artifact.manifest`（来源产物清单）、`artifact.archive`（归档）、`artifact.restore`（恢复）、`artifact.inspect`（检查）、`artifact.release`（释放）、`artifact.candidates.inspect`（候选对象检查）、`artifact.candidates.prune`（候选对象清理）。

**影响：** 新模块不是完全未装配，但从正常模型工具入口发现/执行存在断点。`service.ts`（代理服务）提示词里写出工具名字，不会自动放开 `perform_action`（执行工具）权限。此前隔离测试直接调用工厂函数或自建运行时，绕过了这一层，因此不能证明会话全链已接通。

建议：复用现有允许表和参数/资料范围校验接入七个动作；释放与候选清理必须继续经过独立授权。新增“真实会话 → list_actions → perform_action → 实际宿主”的集成测试，不能仅向 Set 中添加名字后就宣布完成。

### A02｜高：本地释放检查与真实数据库字段不一致

证据：`modules/collection/artifact-lifecycle.ts` 的 `artifactReleaseBlockers`（释放前依赖检查）、`processing-plan.ts` 与 `segments/service.ts` 的真实建表结构，以及实际宿主探针。

| 守卫查询 | 真实表字段 | 实际结果 |
|---|---|---|
| `segment_requests.binding_json` | `input_json` | `segment_requests-unverifiable`（片段请求引用无法核对） |
| `processing_plans.document_json` | `plan_json` | `processing_plans-unverifiable`（加工计划引用无法核对） |

即使新建生成文件没有业务下游依赖，只要完整服务的这两张表存在，查询也会因为列不存在进入保守阻断。因此实际工作区中的 `artifact.release`（本地释放）无法按前述理想流程成功。

安全效果是“保留文件”，不是误删；功能效果仍然是“闭环未通”。建议按真实 schema（数据库结构）修正查询并补全真实宿主测试，不得简单删除异常捕获或忽略未知引用。

### A03｜高：Linux 原生可选依赖选择同时要求 GNU 与 musl

证据：`platform/plugins/direct-versions.ts`，可选依赖按 `dependency.includes(platform-arch)` 选择；实际 `captureVersions`（冻结动作版本）探针。

在当前 Linux x64 宿主，`artifact.manifest` 和 `artifact.candidates.inspect` 尚未执行便返回 `DIRECT_DEPENDENCY_UNAVAILABLE`（实际依赖无法核对），原因是要求未装载的 `@openclaw/fs-safe-linux-x64-musl`。当前选择规则没有区别 GNU/glibc 与 musl 两类系统运行库制品。

**影响：** 它不只影响归档，还可能使依赖公共文件安全模块的多个确定性动作在 Linux 上无法创建有效任务。这不是仅靠“补装所有平台包”就应该解决的问题。

建议：依据实际装载的原生实现或准确的系统运行库选择包，继续保留版本核验；不能关闭整段依赖检查。

### A04｜中：新增实现没有完整纳入动作源码指纹

证据：`platform/plugins/direct-versions.ts` 的 `groups`（实现分组）与 `apps/server/capabilities.ts` 的 `directDependencyVersions`（动作版本绑定）。

新归档工具的绑定沿用 `assembly`（装配）、`baidu`（网盘技能入口）和 `process`（进程）等分组，而新 `artifact-*.ts`、`candidate-reclaim.ts` 及存储归档实现并未全部列入实际源码指纹组。版本字符串存在，不代表实现字节已经被校验覆盖。

**影响：** 部分新实现发生变化时，旧任务的实现指纹可能无法准确体现变化。建议补充最小实现分组，并测试修改对应文件后旧任务被阻断；避免把全仓源码全塞进所有动作的版本计算。

### A05｜中：会话关系与未来消费者尚无完整生命周期

`artifactReleaseBlockers`（释放前检查）将任何 `conversation`（会话）关系视为阻断。真实宿主给生成文件增加会话关系后，探针增加 `other-file-relations`（其他关系占用）。

这符合当前保守安全策略，但意味着“会话产物已归档 → 可清理本地”并不普遍成立。历史会话记录、真正还需要字节的消费者、可从网盘恢复的引用没有被完整区分。`artifact.restore`（恢复）产生新的文件编号，也没有把旧消费者自动迁移到新编号。

建议先定义“历史证据引用”与“仍需要本机字节的消费引用”，再逐入口增加明确恢复/迁移。不能通过一律忽略会话关系来达成清盘指标。

## 三、需要进一步验证的功能与设计风险

1. `artifact.restore`（恢复）统一发布 `.bin`（通用二进制后缀），未保留原始显示文件名和类型。通用转换中部分格式会使用扩展名提示，需针对 CSV、字幕和纯文本恢复后再次入材料/转换的语义验证。本轮标为后续兼容风险，不把所有恢复都判定为失败。
2. `candidate-reclaim.ts`（孤立候选回收）使用固定表/列扫描，必须与真实加工、材料、R1、算法等引用模型逐项比对；旧计划仍引用的候选不能因为已发布就视为垃圾。本轮证明了配置/字段偏差风险，未对生产对象执行清理。
3. `material.ocr`（材料 OCR 适配入口）尚未接入；`image.ocr`（模型图像识别）是不同工具，不能将两者混画成全部可用。
4. 视频、音频、Polars 与 WFD 依赖受信程序、模型文件和 Python 环境。缺少这些资源时的不可用属于条件装配，不等于对应源码是死代码。
5. `external.bd`（外部插件接口）明确保留但未启用。当前仓库的批次处理也不能替代完整历史模拟、训练和独立评测系统。
6. 源码仍有 Pi 模型适配/runtime（运行时）及相关依赖。图按代码标示，不把先前“移除 Pi”的目标当作已完成事实。

## 五、模块与内部线路裁决

| 模块组 | 已追踪的接线 | 当前裁决 |
|---|---|---|
| Web / server（界面与服务） | 启动脚本 → 宿主 → 路由和服务装配 | 有实际接线；并非所有资源与路由在每个角色都启用 |
| agent（会话代理） | 输入规则 → 会话状态 → 模型工具 → 任务与结果 | 主链存在；新增产物工具在允许表处断开 |
| source / conversion（来源与转换） | 来源设置、插件路由、文件身份、转换与转写 | 条件装配；公共版本核对在 Linux 有阻断 |
| collection（数据生产） | 原件保管、语义、加工计划、共享候选对象 | 主调用链存在；语义未知与用途资格仍须独立处理 |
| R1 / database adapters（正式交接） | 受控 Python 请求 → WFD → 固定读回 → 行版本关联 | 代码链存在；生产 Python、快照与真实数据未验收 |
| retrieval（读取与检索） | HTTP 条件读取、固定产品读取、正文索引与来源追溯 | 主链存在；全仓测试仍有检索契约失败 |
| financial（固定算法） | 本地算法或 Polars → 独立核对 → R1 回写 | 两条独立线路，不是所有读取都必须经过算法 |
| artifacts / storage（归档与回收） | 工厂装配 → 注册 → 网盘后端与持久回执 | 模型入口与完整宿主回收均有已确认断点 |
| platform（运行保障） | 任务、授权、版本、资源、进程、状态数据库 | 核心存在；原生依赖选择与新实现指纹覆盖待修 |
| scripts / staging（维护与过渡入口） | 显式采用、迁移、核验及配置选定入口 | 独立工具不能误算为自动日常链；部分可去重 |

总图保留四条业务主线：会话循环、数据生产、数据输出、产物生命周期。内部拆为七图：①会话；②来源与转换；③加工/R1/发布；④读取检索；⑤算法/派生回写；⑥归档恢复回收；⑦启动/授权/版本/持久化。
